# Incremental roadmap

This roadmap implements the greenfield master brief expressed in the [README](../../README.md) and [charter](../business/project-charter.md). It does not inherit a hackathon challenge sequence and is separate from Agentic SDLC work. **Milestones 1–4 are delivered within their recorded scope; Milestones 5–12 are PLANNED and not started.** Runtime evidence comprises the Python foundation and offline dataset tools, not a processing service. Each milestone ends with reviewable evidence and an explicit status update.

| Milestone | Scope and expected deliverables | Exit evidence |
| --- | --- | --- |
| 1 — Charter and architecture baseline | Business scope, architecture/security, evaluation/deployment strategies, roadmap and `.gitignore` | Document/link/consistency checks; no runtime claims |
| 2 — Python engineering foundation | Versioned claim/evidence/policy/assessment/review models; deterministic transitions; local settings/redacted logs; typed protocols; packaging and quality tooling | Local unit tests, lint/format, strict typing and package checks; synthetic examples only; no API, persistence or policy engine |
| 3 — Business process and architecture refinement | Manual/target workflow, role responsibilities, stable requirements/acceptance, traceability, risks and essential ADR | Documentation/link/symbol/status consistency; no runtime changes or new test-run claim |
| 4 — Synthetic motor claims dataset and ground truth | Seeded PDF/PNG fixture authoring, 12 development scenarios, draft policy versions, typed source-linked annotations and integrity/reproduction checks | Unit/lint/type checks, exact regeneration and readable-artifact verification; no approved coverage outcomes or live processors |
| 5 — Evidence ingestion | FastAPI/local persistence skeleton deferred from initial M2 plan; quarantine/scan boundary, upload validation, immutable hashes, extraction adapters and photo-evidence contracts; initial outbox/worker processing | Valid/invalid file tests, provenance checks, restart/replay tests; label stubs simulated and distinguish later authorized Document Intelligence/model tests |
| 6 — Version-aware RAG and rules | Owner-approved policy ingestion, immutable index versions, hybrid retrieval adapter, exact policy resolver and executable rule packs | Policy/endorsement date boundaries, retrieval filters/recall and arithmetic/unknown-fact tests; no model-owned rules |
| 7 — Bounded agent workflows | Agent Framework orchestration, evidence reconciliation and policy explanation; typed tools and model adapters | Tool/output validation, bounded execution, abstention and comparison to simpler baselines; pinned versions |
| 8 — Human review and case outcomes | Reviewer UI, evidence correction, supervisor routing, stale-write protection, audited outcomes | Human approval/override and case reopening tests; no autonomous final decisions |
| 9 — Governed tools and security hardening | MCP/APIM adapter/contracts, Entra authorization, managed-identity design, least privilege, injection defenses and threat model | Local negative/security tests; later cloud identity/gateway evidence explicitly separate; no deployed bypass |
| 10 — Reproducible quality and operations | Independently reviewed held-out golden suite, evaluation manifests, OpenTelemetry instrumentation, dashboards/alert definitions, fault-injection and incident/recovery runbooks | Reported counts/results, safety gates, redaction, replay and dependency-failure evidence; M4 development labels are not held-out evaluation results |
| 11 — Governed Azure deployment | Bicep, protected GitHub Actions/OIDC, environment separation, compatibility/quota matrix and approved budgets | Authorized deployment only: reviewed infrastructure plan, actual service integration/identity tests, smoke checks and cost evidence |
| 12 — Readiness and portfolio evidence | End-to-end synthetic demonstration, restore/recovery exercise, architecture reconciliation, limitations and teardown plan | Traceable implemented/tested/simulated/planned matrix; evaluation, security and operational reports; no unsupported production-readiness claim |

Security, tests, provenance, basic telemetry and cost limits start with their first relevant component; later milestones deepen them rather than defer all controls. No milestone is complete solely because code exists. Actual Azure calls in any milestone require separate deployment/spending authorization; local progress uses explicitly labeled simulations where necessary.

Working definitions: **IMPLEMENTED** means an artifact/code path exists; **TESTED** adds a named environment and recorded checks/results; **SIMULATED** means a stub or injected scenario exercised a contract without proving the live dependency; **PLANNED** means intended only. Track capability and environment separately; documentation completion never promotes runtime status.

Approved requests govern milestone scope: M2 narrowed delivery to foundation code; M3 inserted business/architecture documentation; M4 now inserts the synthetic development corpus before ingestion. Ingestion moves to M5 and later planned milestones shift to M6–12. Draft wording/schedules exist in M4, but rule execution still requires fictional policy-owner approval before M6. These are sequencing changes only; historical [M2](milestone-2.md)/[M3](milestone-3.md) records retain their then-current plans. Contracts and architectural decisions are preserved; see the [M4 record](milestone-4.md).
