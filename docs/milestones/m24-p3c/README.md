## Why the bootstrap failed

P3B attempted only `/usr/bin/sandbox-exec -f <private-profile> /usr/bin/true`. It returned **71** after 0.006855 seconds with `sandbox-exec: sandbox_apply: Operation not permitted`; the test program never launched. No network, write-denial or resource-enforcement result can be inferred from that failure. Receipt/profile hashes still match P3B's decision.

The locally installed Apple SDK's `usr/include/sandbox.h` states that a new profile is ignored and `sandbox_init()` returns an error if the process is already sandboxed. It marks that legacy API **No longer supported** and recommends **App Sandbox** instead. The local `sandbox-exec(1)` manual also marks the executable deprecated. This is consistent with attempting legacy policy installation inside this managed execution context. It is the leading explanation, **not a proven identification of the denying ancestor/profile or syscall policy**: `Operation not permitted` alone is not unique evidence of its cause.

Read-only `ps` inspection was denied (`operation not permitted`, exit 127); querying `kern.hv_support` was also denied (exit 1). The process ancestry, exact restricting profile and usable virtualization support could therefore not be established. No elevation, permission change, sandbox retry or alternative tool was used to bypass those denials. P3B was not a timeout: its configured CPU/file/FD limits are not evidence of the failure's cause, nor of successful enforcement. There is no positive evidence of a malformed profile; syntax acceptance was not independently proved.

## Minimal recommended design and verification plan

Recommend **one local App Sandbox host runner, running as the normal user in an explicitly approved host launch context**, reusing the existing macOS Python/dependency versions. This avoids acquiring a guest OS and a second dependency environment. It is a new host utility requiring separate implementation/review approval, not a request to weaken the current agent sandbox, use an unsandboxed fallback or run G1 now.

1. **Resolve feasibility before coding the controller.** Specify the signed app/helper packaging, executable/library identities, read-only grants, network entitlements and actual child launch chain. Identify every writable container, HOME/cache/temp path and map it to a new declared `$M24_RUN`; no broad home/repository grant. Confirm the launch context can enforce the policy without elevation. Do not assume arbitrary external Python/framework helpers acquire the required policy automatically. If necessary packaging or signing changes cannot be made within separately approved artifact scope, stop.
2. **Resolve the aggregate bound.** Choose and independently verify a supported scratch-cap mechanism enforcing the unchanged **1 GiB aggregate new-state ceiling**, including logs, temporary files and writable container paths. A directory-size poll or `RLIMIT_FSIZE` alone is not proof of that ceiling. Retain five minutes per invocation and thirty minutes per session. A hard memory/process-tree policy, bounded output capture and supervisor termination/reaping must be specified; no resource-enforcement PASS exists yet. If the strict scratch/path bound cannot be supplied, this candidate remains NO-GO rather than gaining a waiver.
3. **Prepare an independently controlled launcher.** Close inherited descriptors except approved private pipes/stdio; do not pass writable handles to history, source, databases or control records. Local `sandbox(7)` warns that already-open descriptors can retain access despite later resource restrictions. Apply hard limits before payload launch, keep the supervisor/control records outside payload write authority, sanitize environment, and use new exclusive private directories. No historical file chmod, rename, repair or database connection is necessary.
4. **Authorize harmless verification only.** First prove permitted private writes and read-only source access. Then test denied numeric loopback TCP/UDP access, IPv4/IPv6 listeners and named local socket/listener paths as applicable, without contacting external hosts. Verify necessary unnamed local IPC separately. Test write-open denial on actual protected paths without truncation/writes; destructive rename/unlink/truncate/symlink/hardlink cases use disposable equivalents only. Repeat in exec child/grandchild, including isolated Python `-I -B`; inspect actual inherited limits, descriptors and writable paths. Never infer denial from a refused connection or an absent file.
5. **Prove controller failure paths.** Exercise harmless CPU/time/file/capture-budget probes and the aggregate cap. Omit or alter each required policy/hash/limit/root in turn; the launcher must reject **before** starting a marker payload. An expired/aborted verification receipt must not authorize a later run. Retain complete safe failures, process cleanup observations, profile/binary/input/output hashes and pre/post historical checks. No fallback to uncontained execution.
6. **Only then request G1 twice.** A complete isolation receipt, reviewed packaging, supported launch context and unchanged P2/P3A limits must precede separate demonstration approval. Native imports and G1 success remain untested. If the App Sandbox design fails feasibility, return for separately approved VM design; do not launch the installed VM or acquire artifacts automatically.
