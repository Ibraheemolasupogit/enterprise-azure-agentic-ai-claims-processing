# Independent review checklist

All boxes start unchecked. Complete a separate actual review record for every case; this document itself asserts no review or approval.

## Integrity and provenance

- [ ] Obtain candidate and packet pins independently; verify all eight frozen files, case/input/proposal/review hashes, asset UTF-8 hashes and the exact 60-case roster/cohort distribution.
- [ ] Inspect original decoded asset content at the specified JSON pointer/native line. Verify all source quotes and explicit absence/conflict cases; hash agreement alone does not establish a correct label.
- [ ] Confirm claim/policy/asset ownership and BUNDLE equality. Check that a cited clause exists in that exact case's policy asset, not merely in another version or generated guide.
- [ ] Confirm all sources are fictional native text. Mark actual scanned-image/OCR, model, provider, identity and live operational capabilities unavailable where unsupported.

## Correctness and ambiguity

- [ ] Check all five critical fields, normalization, amount units and currency. Distinguish omitted predictions from explicit unknowns; never silently populate a missing/conflicting source from intake metadata.
- [ ] Inspect both FORM and ESTIMATE when dates/vehicles conflict. Explain each of the ten null field proposals using absence, UNKNOWN, malformed input or conflict; do not choose a convenient value to improve accuracy.
- [ ] Check inclusive inception/exclusive expiry and exact selected policy version. At v1 expiry, do not silently switch to v2. Retain unresolved versions, endorsements/registers/indexes as ambiguity rather than invented applicability.
- [ ] Recalculate every asserted illustration in integer pence: v1 excess 25,000; v2 excess 40,000; cap 300,000. Review zero, below/equal/above excess and cap boundaries. A zero/net illustration is not a financial recommendation or automatic outcome.
- [ ] Distinguish excluded hypotheses from unsupported/undetermined/not-applicable cases. Review clause relevance, rule findings, supervisor routing, denial/recovery expectations and all five prohibited-action categories.
- [ ] Separate evidence from scenario assertions. A fault string describing overlap, a copied session, revoked grant, failed exporter or crash does not supply the actual register/session/ledger/exporter/process setup. Record the missing adapter/positive control and capability evidence.
- [ ] Define the actual query/answerable-query inventory and applicable source/service mapping before any recall/rule/grounding scoring. M22 proposals do not automatically match M9 operational fixtures; policy approval is separate.
- [ ] For each ambiguity or disagreement, give source rationale and choose ACCEPT_PROPOSAL, REJECT or REQUEST_CORRECTIONS. Source/label/gate/roster corrections require a new version; retain the current v1 unchanged.

## Independence, exposure and leakage

- [ ] Record the actual reviewer's identity/role, conflicts, authoring/tuning involvement, previous access to inputs/labels/code/reports and any known training/model exposure. Do not infer independence or invent an attestation.
- [ ] Decide whether author visibility, scenario/fault hints and prior exposure invalidate a blind/held-out claim. Independent review alone cannot undo exposure; require fresh reviewer-supplied cases/version where necessary.
- [ ] Keep this label-bearing packet and completed review/release records away from prediction inputs, prompts, tools, runtime logs/telemetry and tuning. Only the two frozen input files belong to the input-only handoff.
- [ ] Require a real access-isolation plan and prediction code/prompt/tool/model/environment freeze before future prediction access. DTO separation and trusted subprocess import isolation are not a hostile-code filesystem sandbox.
- [ ] Verify original labels/templates still say PENDING_REVIEW, actual identities/approvals/signatures remain null in preparation artifacts, and no runtime path reads this packet. Review-only case acceptance grants no canonical human/session/case/policy/outcome authority.

## Adjudication and separate release decision

- [ ] Resolve all 60 cases or define a new reviewed version with an explicit roster; retain rejected/correction requests rather than silently removing hard cases.
- [ ] Keep source-rationalised per-case adjudication separate from release approval. Authenticate any actual completed review against independently retained identity/attestation provenance; hashes/status strings are not identity proof.
- [ ] Have a real release owner review independence/exposure, label freeze, exact schema/policy/rule/index/service mapping, predictor isolation and every one of the 12 frozen gate definitions, denominators and applicability decisions.
- [ ] Preserve null/NOT_TESTED for unavailable or unreviewed quality/cost/performance/human-study metrics. Missing predictions count within eligible denominators; harness errors mean incomplete/NOT_TESTED; observed safety violations remain FAIL.
- [ ] Retain worst-case safety failures and cohort denominators. Author-visible SIMULATED development conformance and 17 separate operational controls cannot establish independent 60-case quality.
- [ ] Leave scoring disabled and benchmark unreleased. Runtime independent-review verification remains unconfigured; real scoring/release integration requires separate authorisation. No cloud, live model/identity, spending or M23 work follows from this review.
